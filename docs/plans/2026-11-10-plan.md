# MQTT Navigator — Plan

Writing rule: this plan and all project documents use ASD-STE100 (short sentences, active voice, one instruction per sentence).

## Context

mqtt-pathfinder is an Electron/React MQTT inspector (a fork of MQTT Explorer). It browses a live topic tree, shows message values and history, and publishes messages. It is large, it starts slowly, and its documents record known weak points:
- no tree virtualization;
- MQTT runs in the Electron main process, one IPC send per message;
- no global memory budget;
- TLS validation is off by default;
- most MQTT 5 properties are missing.

We will build **MQTT Navigator**: a native Rust desktop app with the same purpose. It must start fast, use little CPU and memory, run for days without leaks, and be secure. It runs on Windows, Ubuntu and macOS.

**Product scope (owner, 2026-11-10).** The app has two major features: **Subscribe** and **Publish**. All other parts exist only to support these two features. Keep the app simple.

Stack (given by the user): `ms-mqtt-client` (microsoft/rust-mqtt-client), `gpui-kit`, windows-rs only if needed.

Decisions from the user:
- Update source: public GitHub Releases of `pauldeng/mqtt-navigator`.
- Signing: an Ed25519/minisign update-manifest key and a Windows Authenticode certificate. There is no Apple Developer ID.
- v1.0 scope:
  - Subscribe, with two switchable views of received messages: a topic tree and a newest-first message list;
  - Publish;
  - support features: saved connection profiles, TLS/mTLS, MQTT 5 properties, per-topic history and auto-update.
- Rust: always the latest stable toolchain. Do not pin a version.
- Release targets: Windows x64, macOS arm64 and x64, Linux x64.
- Not in v1: proxy support, message export, accessibility (screen readers).
- License: MIT OR Apache-2.0.
- MQTT 5 only, QoS 0/1. This is a limit of the library.
- Binary size: measure a baseline in P1. Set the CI gate at the end of P5, at the measured value + 10%.

## Architecture

### Crates (fewest that keep the core testable without a GPU)

```
mqtt-navigator/
  Cargo.toml                 workspace, latest versions (Cargo.lock), release profile
  crates/navigator-core/     no gpui. MQTT session, topic store, decoders, profiles, settings
  crates/navigator-app/      gpui-kit UI, updater, main(). Binary name: mqtt-navigator
  docs/  mockups/  .github/workflows/
```

CI checks that `navigator-core` never depends on gpui.

### Threads and data flow

```
 gpui main thread                         "net" thread (tokio current_thread runtime)
 ┌──────────────────────────┐  Command   ┌─────────────────────────────────────┐
 │ UI entities              │──bounded──▶│ Supervisor: state machine,          │
 │ TopicStore (owned here)  │   (64)     │ reconnect + backoff, resubscribe    │
 │ drain task: await first  │            │ Session task: ms-mqtt-client        │
 │ msg, then try_recv batch │◀──bounded──│ try_send Incoming; on Full: drops++ │
 │ ≤ 4 ms / frame, notify() │  (50 000)  │ (AtomicU64, shown in status bar)    │
 │                          │◀─ watch ───│ current state (coalesced) + bounded │
 │                          │── cancel ─▶│ error/result log; all tagged with   │
 └──────────────────────────┘            │ connection generation               │
                                         └─────────────────────────────────────┘
```

- `Command` enum: `Connect(Profile)`, `Subscribe`, `Unsubscribe`, `Publish{op_id}`, `ClearRetained`.
- Disconnect and shutdown do not use the command queue. They use their own `watch` cancel signal, so a full publish queue cannot delay them.
- `Qos` enum has only `AtMostOnce` and `AtLeastOnce`. QoS 2 cannot be expressed.
- Ingest queue: bounded by count (50 000) **and** by bytes (32 MiB in flight). A full queue drops the message and increments `drops`.
- Status: a `watch` channel holds the current state, so updates coalesce and the sender never blocks. Errors and command results go to a bounded log (256 entries, drop oldest).
- **Generations:** each connect gets a `generation: u64`. Every message, status and result carries it. The UI rejects stale generations. The supervisor cancels and joins the old session before it starts a new one.
- **Drain loop with a hard frame budget:**
  1. Wait on `recv().await`. Idle CPU is ~0.
  2. Merge a batch until 4 ms have passed. The 4 ms includes the visible-row rebuild.
  3. Call `cx.notify()`.
  4. Wait on a 33 ms timer, then loop. Under backlog the UI thread is busy at most ~12% of the time.
- **Publish result:**
  - QoS 0: "Sent". It is never shown as acknowledged.
  - QoS 1: "Acknowledged", "Rejected (reason code)", "Timed out" (10 s) or "Lost on disconnect". Each is matched by `op_id`.
- **Event-driven and responsive** (owner requirement, 2026-11-10). See ARCHITECTURE.md "Event-driven design" and "Responsive UI":
  - All work starts from an event. There are no polling loops, and the app does not wake up when idle.
  - The UI thread does no blocking I/O.
  - Large payload decoding runs in the background and can be cancelled.
- **Incoming size limit:** CONNECT advertises Maximum Packet Size (default 2 MiB). P1 checks that the pinned client rejects a larger incoming packet or WebSocket frame before it allocates. If it does not, we wrap the transport with a length check.
- Session states: `Disconnected → Connecting → Connected → Reconnecting{attempt} → Disconnecting → Disconnected`. Shutdown has its own state, so an intentional disconnect never looks like a transient close (this is the pathfinder listener bug).
- Panic containment: the session runs in a spawned task. A `JoinError` with panic becomes `Status::Failed`, then a clean disconnect and an error banner. The release profile uses the default `panic = "unwind"`.

### TopicStore (in `navigator-core`, pure and unit-tested)

- Arena `Vec<Node>`. Each node has `children: BTreeMap<Box<str>, NodeId>` (sorted for free), `parent`, `msg_count`, `subtree_msgs`, `subtree_topics`, `last: Option<Msg>`, `retained`, `last_seen`, `history: VecDeque<Msg>`.
- `Msg` keeps the payload as `bytes::Bytes` only if the payload is under the limit. A truncated payload is **copied** (`Bytes::copy_from_slice`), so a short slice never keeps a large buffer alive. It also stores MQTT 5 properties, QoS, retain and a timestamp.
- **One store budget (default 256 MiB, user-settable)** covers all of these:
  - latest values;
  - history;
  - properties;
  - node metadata (fixed overhead estimate per node, plus name bytes).
- Other limits:
  - latest value: up to 1 MiB, then truncated with `truncated` and `original_size`;
  - history: 100 messages per topic, payloads up to 64 KiB;
  - topic count: 200 000. New topics above the cap are counted as `topic_drops` and are not stored.
- **Admission control.** The store computes the cost of each message **before** it inserts the message. It inserts only when the cost fits:
  1. If the cost does not fit, evict until it fits. The eviction order is:
     - the oldest message-list entries;
     - the oldest history entries;
     - the oldest latest-value payloads. An evicted latest value keeps its metadata and shows "payload evicted".
  2. Node metadata cannot be evicted. Node metadata (overhead plus name bytes) has its own cap: 25% of the store budget. It also has the topic cap.
  3. If a new topic does not fit in the node cap, reject the message and increment `topic_drops`.
  4. If a message still does not fit after eviction, reject it and increment `drops`.
- Test: the store never goes above its budget. Use long topic names, large payloads, many topics and an empty history.
- Global FIFO of `(NodeId, seq)`:
  - On pop, skip the entry if that node's ring front has a different `seq` (a stale entry from a per-topic eviction).
  - Compact the FIFO when its length is more than 2× the live entries.
  - Test with empty and 1-byte messages.
- **Message list** (the second view): a bounded newest-first `VecDeque<(NodeId, Msg)>` with up to 10 000 entries. Each entry counts its full payload bytes in the store budget, even if history holds the same `Bytes`. This over-counts on purpose: the budget is then an upper bound. The filter matches the topic, or the text in the first 1 KiB of the payload.
- **Selected message:** the UI holds one clone of the selected `Msg` (a cheap `Bytes` reference, at most 1 MiB). It stays visible after the store evicts it. This is the only data outside the budget.
- Count raw payload bytes (pathfinder counted base64 by mistake). Validate all limits at the boundary: reject NaN, negative and zero.
- Visible rows: a flat `Vec<NodeId>` of the expanded nodes. Rebuild it only when structure, expansion or the filter changes. Read counts at render time. Render with a virtual list. In P1, check whether gpui-kit `Tree` virtualizes; otherwise use `uniform_list`.
- Filter: substring match on the full path, debounced 150 ms. Matches keep their ancestors visible.

### Security

- TLS is **on** by default: a new profile uses TLS on port 8883. The user can select TCP or WS in the connection form, and the app then shows a "Not encrypted" warning.
- TLS certificate verification is **on** by default. An "Allow insecure TLS" toggle shows a permanent red badge.
- Custom CA, client certificate and key (PEM). Files are read at connect time from stored paths.
- Map each OpenSSL verify error to a plain cause: expired, hostname mismatch, unknown CA, bad client key.
- Secrets (password, key passphrase) go only in the OS keyring (`keyring` crate). If no keyring is available, keep them in memory for the session and show "not saved".
- Settings are JSON with `schema_version`. Write them atomically (temp file, fsync, rename). A corrupt file is renamed `.bad` and reported. It is never silently discarded.
- Logs go to the platform log directory. Size cap: 5 MiB, with 1 previous file kept. Never log payloads or secrets. A panic hook writes a crash file.
- No telemetry.
- The only network traffic outside the broker is the update check. It can be turned off.
- `unsafe_code = "forbid"` in `navigator-core`. Any `unsafe` in the app (for example windows-rs) needs a `// SAFETY:` comment.
- `cargo-deny` checks advisories, licenses (allowlist) and duplicates.

### Dependencies (each needs a reason; add no others without one)

`gpui-kit`, `ms-mqtt-client` (+`websockets`), `openssl` (`vendored`), `tokio` (`rt`, `sync`, `time`), `bytes`, `serde` + `serde_json`, `keyring`, `dirs`, `thiserror` (core), `anyhow` (app), `tracing` + `tracing-subscriber`. Updater dependencies are chosen in P6.

### Release profile

P1 to P4 use `opt-level = 3`, `lto = "thin"`, `codegen-units = 1`, `strip = true`, `debug = "line-tables-only"`, `split-debuginfo = "packed"`. The panic strategy stays unwind. The debug information goes to a separate file (`.dwp`, `.dSYM`, `.pdb`), so the shipped binary stays small. P6 stores these files as release artifacts for crash analysis. P5 compares `opt-level = "s"` and `lto = "fat"` before it sets the size gate.

## UI/UX design

The full design is in [docs/ui-design.md](../ui-design.md). Summary:
- Use gpui-kit components only. There is no webview and no web UI.
- Theme: System (default), Light or Dark. System mode follows the OS through an appearance event.
- Layout (learned from MQTT Explorer, MQTTX and mqtt-spy; see the UI doc section 2):
  - Title bar: profile select, connection state, filter, command palette, and Connect or Disconnect.
  - Left pane: subscriptions. Type a filter and press Enter. Each subscription has a colour. A click filters the messages.
  - Centre pane: a "Messages | Tree" switch (Messages is the default), and an always-visible publish composer at the bottom. Sent messages show in the list too.
  - Right pane: details (Value, History) and actions that fill the composer but never send: "Publish to this topic", "Edit and publish", "Reply" (MQTT 5 Response Topic). "Clear retained" is separate.
  - Status bar along the bottom.
- The connection editor is a right-side sheet.
- The HTML files in `mockups/` are design references only.

**P1 — Tracer bullet (the core path end to end).**
- The tracer bullet covers both major features end to end:
  - connect to Mosquitto (localhost, profile from CLI arguments);
  - subscribe to one filter (default `#`);
  - show a virtual topic tree with counts;
  - select a topic to see its latest payload as text;
  - publish a text payload (QoS 0/1) and show the result;
  - disconnect cleanly.
- Include the minimum bounds now:
  - the queue limits (count and bytes) and the drop counter;
  - latest value only (no history yet);
  - the topic cap;
  - the generation ID;
  - the cancel signal.
- Add `examples/flood.rs`, a load generator built on ms-mqtt-client.
- Measure the gpui-kit `Tree` with 100k topics that change all the time. Its `set_items` and expand rebuild all entries. If one frame takes longer than 4 ms, use our own flat row list on `uniform_list`. Record the decision in an ADR.
- Check the incoming packet-size behaviour of the client (see Threads).
- **Exit criteria.** Load: 10k msg/s, 10k topics, 100-byte payloads, 60 s warm-up, then 5 min measured.
  - UI frame time p95 < 16 ms. Input-to-frame latency p95 < 50 ms.
  - Idle and disconnected for 60 s: no periodic wake-ups. Measure with `voluntary_ctxt_switches` in `/proc/<pid>/status` (Linux).
  - No drops at 10k msg/s.
  - RSS growth after warm-up < 10 MiB.
- **Overload test:** 50k msg/s for 60 s.
  - Drops are counted and shown.
  - The UI stays responsive.
  - Rate and RSS return to normal within 10 s after the load stops.
- Measure on each OS with one release profile (`lto = "thin"`): cold start to first frame, idle RSS, idle CPU, binary size. Record these as the **baseline**. Do not do profile sweeps yet.
- Prove in CI: a vendored OpenSSL build on Windows (needs Perl and NASM) and on macOS.
- Set provisional start-time and RSS budgets. Set the final size gate at the end of P5 (measured + 10%), when the features are complete.

**P2 — Session robustness.**
- State machine, backoff with jitter (1 s → 30 s), resubscribe after reconnect, CONNACK and SUBACK reason codes shown in the UI, granted QoS stored.
- The Subscriptions panel: add and remove filters while connected, with SUBACK results.
- TLS diagnostics, panic containment, logging.
- Real-broker integration tests: Mosquitto 2.x in Docker with listeners for anonymous TCP, auth, TLS, mTLS, WS and WSS. Readiness is a polled real connect.
- Tests prove no delivery after disconnect and recovery after a broker restart.

**P3 — Store and flow control.**
- Ring buffers, global budget, truncation, drop counters, pause (ingest continues inside the budget), filter, tree a–z order. The message list is always chronological.
- The Messages view (default) with 2-line rows (full-width payload preview) and a 1-line option, the long-payload rules of the UI doc section 3.3, the "Messages | Tree" switch, the All / Received / Sent filter, subscription colours and click-to-filter.
- Unit tests for every budget path.
- Load test in CI.

**P4 — Profiles and persistence.**
- Connection editor, atomic versioned settings, keyring secrets, certificate paths. The profile stores its subscriptions.
- Profile export and import as JSON (connection profiles only; message export is not in v1). Exports never include secrets. Import never overwrites an existing profile.

**P5 — Inspector and full publish.**
- The full composer: Text/Hex payload, MQTT 5 properties, History ▾ (last 20 publishes of the session), "Publish to this topic", "Edit and publish" (exact bytes), "Reply" (Response Topic).
- Decoders (fuzz each decoder with `cargo-fuzz`), MQTT 5 property view, history table, publish with MQTT 5 properties, clear retained, copy, theme, settings, shortcuts.

**P6 — Release and auto-update.**
- Choose the updater with an ADR. Candidates:
  - `cargo-packager` + `cargo-packager-updater` (last release July 2025);
  - a thin custom updater like Argus (manifest + `minisign-verify` + `self-replace`).
- Required criteria:
  - minisign/Ed25519 signature verified before install;
  - SHA-256 check;
  - HTTPS only from GitHub Releases;
  - Windows replaces the running exe;
  - Linux swaps the AppImage;
  - macOS replaces the .app bundle;
  - rollback if the new version fails to start.
- Packages:
  - Windows: x64 installer and portable exe, Authenticode signed in CI.
  - macOS: arm64 and x64 DMG, ad-hoc codesigned, with documented Gatekeeper first-run steps.
  - Linux: x64 AppImage (self-update) and .deb (updates through the package; the app shows a notice only).
- Every release has `SHA256SUMS` and a signed `latest.json`. The private key is stored only in CI secrets.
- **Update contract:**
  - The minisign signature covers a manifest that binds `version`, `target` (OS and architecture), artifact `url`, `sha256` and `size`.
  - The app rejects any version ≤ the current version, so an old signed manifest cannot be replayed.
  - The download goes to a staging folder. The app checks the hash, then swaps by atomic rename, and keeps the previous binary.
  - The new version writes a "healthy" marker after its first window opens. If the next start finds no marker, a small launcher step restores the previous binary.
  - Tests cover: a bad signature, a hash mismatch, a downgrade, an interrupted download, an interrupted swap, and a new version that fails to start.
